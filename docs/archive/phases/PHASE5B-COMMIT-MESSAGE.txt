feat(phase5): harden durable timer and alarm event handling

Problem:
- Timer completion state could be cleared before notification or foreground-service startup succeeded.
- Timer restore/recovery logic was duplicated across ViewModel, receiver, and boot paths.
- Alarm broadcasts could ring after an alarm had been deleted or disabled.
- Snooze events were indistinguishable from normal alarm events at the receiver boundary.
- Dismissing a ringing alarm could stop the service before the durable trigger transition was committed.

Changes:
- Add TimerDurabilityPolicy for shared recovery decisions.
- Persist completionPending before timer completion side effects.
- Preserve completionPending until the alert path is established.
- Reuse timer recovery policy across app, receiver, and boot recovery.
- Add AlarmTriggerPolicy and explicit snooze metadata.
- Revalidate alarm existence/enabled state in receiver and service.
- Commit alarm trigger state from notification actions.
- Reconcile alarm state before ringtone/vibration startup.
- Order TimerViewModel persistence before scheduler synchronization for critical transitions.
- Add focused pure-policy tests and Phase 5B documentation.

Behavior:
- Process death during timer completion no longer loses the durable completion event.
- Stale normal alarm events are ignored after deletion/disable; explicit snooze remains valid.
- Dismiss/snooze actions preserve the alarm state transition even if the ringing service is stopped early.
- Existing AlarmManager and ChronaTimeEngine contracts remain intact.

Validation:
- Pure Kotlin policy compilation passed.
- Pure policy smoke test passed.
- delay(1000) audit passed.
- No files deleted.
- Full Android Gradle test remains blocked by Gradle 9.7.1 distribution DNS resolution.
